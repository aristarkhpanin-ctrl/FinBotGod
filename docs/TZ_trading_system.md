## 0. Как читать этот документ

Это ТЗ написано для передачи в Claude Code. Заказчик не является программистом
и не умеет читать код. Из этого следует главное проектное требование:

> **Система должна быть проверяема человеком, который не читает код.**

Каждое решение системы обязано быть объяснено одной строкой на русском языке,
которую заказчик может проверить калькулятором за 30 секунд. Всё, что нельзя
объяснить такой строкой, в систему не попадает.

Фазы выполняются строго по порядку. Переход к следующей фазе — только после
выполнения критериев приёмки предыдущей. Не начинать с подключения к брокеру.

## 1. Цель и антицель

### Что строим

Исследовательскую инфраструктуру для проверки торговых гипотез на российском
рынке акций с честным учётом издержек. Основной продукт первых четырёх фаз —
не прибыль, а **достоверный ответ на вопрос «работает ли эта идея после
издержек»**.

### Что НЕ строим

- Не обучаем и не подключаем ML-модели в фазах 1–8. Интерфейсы и инфраструктура
  валидации под них закладываются с самого начала — см. Часть II. Сами модели
  остаются за фича-флагом, выключенным по умолчанию.
- Не строим HFT, скальпинг, торговлю внутри стакана. Минимальный таймфрейм — дневной.
- Не строим оптимизатор, перебирающий сотни параметров.
- Не строим красивый веб-интерфейс. Отчёты — текст и CSV.
- Не подключаемся к брокеру до фазы 5.

### Контекст, определяющий дизайн

- Стартовый капитал для боевого запуска: 20 000 ₽.
- Ключевая ставка ЦБ на июль 2026: 14,25%. Безрисковая альтернатива доступна
  в два клика.
- Инфраструктура стоит ~4 800 ₽/год, что составляет 24% капитала.
- **Следствие: порог безубыточности стратегии — около 38% годовых.**

Этот факт не должен быть спрятан. Система обязана показывать его в каждом отчёте.

## 4. Фаза 1 — Слой данных

### Источник

MOEX ISS API, публичный, без авторизации, бесплатный.

Базовый URL: `https://iss.moex.com/iss/`

Основные эндпоинты (проверить актуальность в документации ISS перед реализацией):

- Список бумаг основного режима T+1:
  `/engines/stock/markets/shares/boards/TQBR/securities.json`
  Отсюда берётся **`LOTSIZE`** — критически важное поле.
- Дневные свечи:
  `/engines/stock/markets/shares/boards/TQBR/securities/{SECID}/candles.json`
  Параметры: `from`, `till`, `interval=24` (день).
- Историческая статистика по торгам:
  `/history/engines/stock/markets/shares/boards/TQBR/securities/{SECID}.json`
  Содержит объёмы и количество сделок — нужно для оценки ликвидности.
- Состав индекса на дату:
  `/statistics/engines/stock/markets/index/analytics/IMOEX.json`

### Требования

1. **Пагинация.** ISS отдаёт данные страницами. Использовать блок `cursor`
   (`INDEX`, `TOTAL`, `PAGESIZE`) и параметр `start`. Не полагаться на то, что
   первая страница содержит всё.
2. **Кэширование обязательно.** Скачанное однажды складывается в Parquet и
   больше не запрашивается. Повторный прогон бэктеста не должен трогать сеть.
3. **Вежливость к API.** Не более 3 запросов в секунду, экспоненциальные ретраи,
   таймаут 10 секунд.
4. **Валидация данных при загрузке.** Проверять: нет дубликатов дат, нет
   пропущенных торговых дней внутри диапазона, `high >= max(open, close)`,
   `low <= min(open, close)`, объём не отрицательный, цена не ноль. Любая
   аномалия — в лог с предупреждением, не молча.
5. **Корпоративные действия.** Сплиты и консолидации ломают ценовые ряды. На
   первом этапе достаточно детектора: скачок цены между соседними днями больше
   35% при отсутствии новостного объёма — пометить бумагу как подозрительную и
   исключить из бэктеста с явным сообщением. Не пытаться корректировать
   автоматически.

### Проблема выживаемости

Если тестировать стратегию только на бумагах, которые торгуются сегодня,
результат будет завышен: обанкротившиеся и делистингованные компании выпадут
из выборки. Это одна из главных причин, почему бэктесты врут.

Требование: универсум инструментов на каждую дату определяется **историческим
составом индекса на эту дату**, а не сегодняшним списком. Если полные
исторические данные недостаточны — зафиксировать это ограничение в отчёте
явным текстом, а не умолчать.

### Критерии приёмки фазы 1

- [ ] Загружены дневные свечи по 30+ ликвидным бумагам за 2015–2026.
- [ ] Повторный запуск загрузки не делает ни одного сетевого запроса.
- [ ] Для каждой бумаги доступен `LOTSIZE`.
- [ ] Отчёт валидации показывает количество найденных аномалий по каждой бумаге.
- [ ] Тест: обрыв сети посреди загрузки не приводит к порче кэша.

## 5. Фаза 2 — Модель издержек

**Это самый важный модуль проекта.** Бэктест без честной модели издержек
покажет прибыльной любую стратегию. Именно так розничные алготрейдеры себя
обманывают.

### Состав издержек на одну сделку

```python
class CostModel:
    broker_commission_pct: float      # % от оборота
    broker_commission_min: float      # минимум в рублях за сделку
    exchange_fee_pct: float           # комиссия биржи
    half_spread_pct: float            # половина спреда, платится на каждой стороне
    slippage_model: SlippageModel     # проскальзывание
```

### Модель проскальзывания

Проскальзывание не константа. Минимальная адекватная модель:

```
slippage_pct = base_slippage + impact_coefficient * (order_value / adv_20)
```

где `adv_20` — средний дневной оборот бумаги в рублях за 20 дней.

Требование: если `order_value > 1% от adv_20`, писать в лог предупреждение.
Если `> 5%` — отклонять сделку как нереализуемую. Бэктест, который «покупает»
объём, недоступный на рынке, бесполезен.

### Налоги

НДФЛ 13% с зафиксированной прибыли. Учитывать в годовом разрезе, отдельной
строкой в отчёте. Показывать, сколько стратегия теряет на налогах относительно
варианта «купил и держу три года» с льготой долгосрочного владения.

### Параметры по умолчанию

Задать в конфиге с консервативными значениями и комментариями на русском.
Обязательно предусмотреть **стресс-режим**: прогон с издержками, увеличенными
в 2 раза. Стратегия, которая умирает при удвоении издержек, не имеет запаса
прочности и не годится для боевого запуска.

### Критерии приёмки фазы 2

- [ ] Юнит-тест: сделка с известными параметрами даёт вручную посчитанный результат.
- [ ] Юнит-тест: минимальная комиссия применяется на маленьких сделках.
- [ ] Юнит-тест: проскальзывание растёт при росте размера заявки.
- [ ] Заявка объёмом 10% от ADV отклоняется.

## 6. Фаза 3 — Сайзинг и лотность

### Расчёт размера позиции

```
target_rubles = portfolio_value * target_weight
lots = floor(target_rubles / (price * lot_size))
actual_shares = lots * lot_size
```

### Обязательные проверки

1. Если `lots == 0` — сделка не совершается, в лог пишется причина:
   «Пропуск SBER: целевая сумма 4 200 ₽ меньше стоимости одного лота 4 850 ₽».
2. Если `actual_shares * price > portfolio_value * max_position_pct` — обрезать
   до лимита, пересчитать лоты вниз.
3. Проверка достаточности денег с учётом комиссии, а не только цены.

### Отдельное требование: отчёт о разрешающей способности

При старте бэктеста система выводит:

```
Капитал: 20 000 ₽
Средняя стоимость лота в универсуме: 4 600 ₽
Максимум одновременных позиций: 4
Минимальный шаг позиции: 23% портфеля
ВНИМАНИЕ: риск-менеджмент с ограничением 2% на сделку нереализуем.
```

Заказчик должен видеть это до того, как посмотрит на кривую доходности.

## 7. Фаза 4 — Движок бэктеста

### Дисциплина времени — защита от заглядывания в будущее

Самый частый и самый разрушительный баг. Решение принято по цене закрытия дня,
а сделка исполнена по цене закрытия того же дня — такая система «знает» будущее
и показывает фантастические результаты, недостижимые в реальности.

**Жёсткое правило:**

- Сигнал рассчитывается по данным, доступным **на момент закрытия дня T**.
- Исполнение происходит по цене **открытия дня T+1** с учётом проскальзывания.
- Никакая функция стратегии не должна иметь доступа к данным после дня T.
  Обеспечить это архитектурно: движок передаёт стратегии срез данных, а не
  весь DataFrame.

### Обязательный тест на заглядывание

Реализовать тест: сдвинуть все сигналы на один день вперёд относительно
исполнения. Доходность должна **заметно ухудшиться**. Если она не изменилась
или улучшилась — в системе есть утечка будущего. Этот тест обязателен и должен
падать при внесении утечки.

### Метрики

Считать и выводить:

- CAGR, максимальная просадка, длительность максимальной просадки
- Коэффициент Шарпа — **с безрисковой ставкой 14,25%, а не с нулём.** Шарп
  с нулевой безрисковой ставкой на российском рынке 2026 года — бессмысленное число.
- Сортино, Кальмар
- Количество сделок, оборот за период
- **Суммарные издержки в рублях и в процентах от валовой прибыли**
- Доля прибыльных сделок, профит-фактор

### Обязательные бенчмарки в каждом отчёте

Три строки сравнения, всегда:

1. Стратегия
2. Купил и держи индекс IMOEX
3. **Фонд денежного рынка под 14,25% годовых**

Если стратегия проигрывает третьей строке — вывести это первым, крупно, до
всех остальных цифр.

### Критерии приёмки фазы 4

- [ ] Тест на заглядывание в будущее реализован и проходит.
- [ ] Тест известного ответа: стратегия «купить в первый день, держать» на
      одной бумаге даёт результат, совпадающий с ручным расчётом до копейки.
- [ ] Отчёт содержит все три бенчмарка.
- [ ] Прогон с удвоенными издержками выполняется одним флагом.

## 8. Фаза 5 — Walk-forward валидация

Бэктест на всей истории с подобранными на этой же истории параметрами ничего
не доказывает. Нужна проверка на данных, которых оптимизатор не видел.

### Схема

```
Окно 1: обучение 2015-2018 → проверка 2019
Окно 2: обучение 2016-2019 → проверка 2020
Окно 3: обучение 2017-2020 → проверка 2021
...
```

Параметры подбираются только на обучающем окне, применяются к проверочному
без единого изменения. Итоговые метрики считаются **исключительно по склейке
проверочных окон**.

### Ограничение на количество параметров

Не более 3 оптимизируемых параметров. Каждый дополнительный параметр
экспоненциально увеличивает риск подгонки. Если стратегии нужно 7 параметров,
чтобы работать, она не работает.

### Учёт множественного тестирования

Если проверено 50 вариантов стратегии, лучший из них выглядит хорошо просто
по теории вероятностей. Требование: система ведёт журнал **всех** проверенных
конфигураций и в финальном отчёте выводит:

```
Проверено конфигураций: 47
Лучшая по OOS-доходности: 18,3% годовых
Медианная по OOS: 2,1% годовых
Поправка на множественное тестирование: результат лучшей конфигурации
не является статистически значимым при 47 испытаниях.
```

Это защита от самообмана, и её нельзя отключать.

### Критерии приёмки фазы 5

- [ ] Метрики считаются только по out-of-sample.
- [ ] Журнал всех проверенных конфигураций сохраняется.
- [ ] В отчёте есть медиана по всем конфигурациям, а не только лучшая.

## 9. Фаза 6 — Риск-слой

**Требование к архитектуре: риск-слой не зависит от логики стратегии.** Он
работает, даже если стратегия содержит грубые ошибки. Это последняя линия
обороны.

### Обязательные предохранители

| Предохранитель | Действие при срабатывании |
|---|---|
| `max_position_pct` — доля одной позиции | Обрезать заявку |
| `max_positions` — число позиций | Отклонить новую покупку |
| `whitelist` — разрешённые тикеры | Отклонить, записать в лог как инцидент |
| `max_order_value` — потолок суммы заявки | **Остановить систему.** Превышение означает баг в расчёте единиц |
| `max_orders_per_day` — потолок числа заявок | **Остановить систему.** Означает зацикливание |
| `daily_loss_limit` — дневной убыток | Закрыть позиции, остановиться до следующего дня |
| `max_drawdown_from_peak` — просадка от максимума | Закрыть всё, уйти в кэш, остановиться навсегда до ручного перезапуска |

Последние два предохранителя работают по **фактической стоимости портфеля**,
запрошенной у брокера, а не по внутреннему расчёту системы. Внутренний расчёт
может быть неверным — в этом весь смысл.

### Идемпотентность заявок

Каждая заявка получает уникальный идентификатор клиента, формируемый
детерминированно из даты, тикера и намерения. При переподключении система
сначала запрашивает у брокера состояние заявок и позиций и сверяет со своим
представлением. **Расхождение — это остановка и уведомление, а не попытка
исправить автоматически.**

## 10. Фаза 7 — Человекочитаемый журнал

### Формат

Два параллельных потока:

1. `decisions.log` — по одной строке на решение, на русском языке
2. `events.jsonl` — структурированный JSON для анализа

### Примеры строк журнала

```
2026-07-23 10:05  ПОКУПКА  SBER  2 лота (20 шт) по 312,40 ₽ = 6 248 ₽
                  Причина: доля SBER 0% при целевой 25%
                  Комиссия: 3,12 ₽ | Проскальзывание: 6,25 ₽
```

### Ежемесячный отчёт

Автоматически, в CSV и текстом: доходность, издержки, число сделок, сравнение
с бенчмарками, список сработавших предохранителей.

## 11. Фаза 8 — Бумажная торговля

Живые данные, реальная логика, заявки не отправляются.

Минимальная длительность: **три месяца**. Сокращать нельзя.

### Что проверяем

- Расхождение между решениями на живых данных и на бэктесте того же периода.
  Расхождение больше 1% по доходности — искать причину, не игнорировать.
- Устойчивость к обрывам связи, выходным, праздникам, дискретным аукционам,
  остановкам торгов.
- Поведение при отсутствии данных по бумаге в конкретный день.

### Критерий приёмки

Три месяца непрерывной работы без ручного вмешательства и без расхождений
с бэктестом, которые нельзя объяснить.

## 12. Фаза 9 — Боевой коннектор

Только после успешного прохождения всех предыдущих фаз.

### Брокер

ALOR OpenAPI — REST для заявок и портфеля, WebSocket для потоковых данных.
Документация: `alor.dev/docs`. У Алора есть тестовый контур — **весь коннектор
пишется и отлаживается на нём**, боевые ключи подключаются последними.

Не использовать QUIK: требует постоянно работающего Windows-VPS, который при
данном капитале стоит 4–7% капитала в год.

### Требования к коннектору

1. Токен доступа короткоживущий. Реализовать прозрачное обновление до истечения,
   а не по факту ошибки 401.
2. При обрыве WebSocket — переподключение с экспоненциальной задержкой и
   **обязательной ресинхронизацией состояния** через REST перед возобновлением
   торговли.
3. Все заявки — лимитные. Рыночные заявки запрещены: при тонком стакане они
   исполняются по неприемлемым ценам.
4. Заявка, не исполненная за N минут, снимается. Система не оставляет висящие заявки.
5. Отдельный аварийный скрипт `emergency_stop.py`: снимает все заявки, закрывает
   все позиции, останавливает систему. Запускается одной командой.

## 16. Главный риск: инструменты ускоряют и исследование, и самообман

С LLM в контуре можно сгенерировать и проверить 500 вариантов стратегии за
выходные. Раньше на это уходил год. Проблема в том, что при 500 испытаниях
лучший результат будет выглядеть блестяще **даже если ни одна из идей не
работает** — это чистая статистика экстремальных значений.

Отсюда центральный вывод для всей Части II:

> Чем мощнее исследовательские инструменты, тем важнее журнал гипотез.
> `research/ledger.py` — самый критичный модуль системы, а не вспомогательный.

### Требования к журналу гипотез

Каждый прогон бэктеста, независимо от способа его запуска, автоматически
записывает в журнал:

- Хеш конфигурации и хеш версии данных
- Полный набор параметров
- Источник гипотезы: человек, LLM, перебор
- Метрики in-sample и out-of-sample
- Временную метку

Отключить запись нельзя. Прогон в обход журнала — считается багом.

### Скорректированные метрики

При наличии более 10 испытаний система обязана выводить вместо обычного Шарпа
**дефлированный коэффициент Шарпа** (Deflated Sharpe Ratio), учитывающий
количество проведённых испытаний и негауссовость распределения доходностей.
Обычный Шарп при этом тоже показывается, но помечается как несостоятельный.

Формулировка в отчёте должна быть прямой:

```
Испытаний проведено: 312
Шарп лучшей конфигурации: 1,84
Дефлированный Шарп: 0,21
Вероятность, что результат получен случайно: высокая
Вывод: гипотеза НЕ подтверждена
```

## 17. Point-in-time хранилище признаков

Признак, посчитанный по данным, которых в тот момент не существовало, —
это утечка будущего в замаскированном виде. На дневных ценах утечку легко
заметить, на производных признаках — почти невозможно.

### Правило регистрации признака

Ни один признак не попадает в хранилище без трёх обязательных полей:

```python
@dataclass(frozen=True)
class FeatureSpec:
    name: str
    compute_fn: Callable
    availability_lag: timedelta   # ОБЯЗАТЕЛЬНО, без значения по умолчанию
    source: str
    description_ru: str           # для человекочитаемого журнала
```

`availability_lag` — задержка между моментом, к которому относятся данные,
и моментом, когда они реально стали публично доступны. Примеры:

| Признак | Задержка |
|---|---|
| Цена закрытия дня | 0 (доступна в момент закрытия) |
| Дневной оборот | 0 |
| Квартальная отчётность | 45–90 дней от конца квартала |
| Дивидендная отсечка | известна заранее, отрицательная задержка |
| Данные Росстата | 20–40 дней |
| Решение ЦБ по ставке | 0, но дата заседания известна заранее |

Отсутствие явно указанной задержки — ошибка на этапе регистрации, а не
предупреждение.

### As-of соединение

Все соединения признаков с ценовым рядом выполняются исключительно через
`pandas.merge_asof` с `direction='backward'` по времени доступности, никогда
по времени события. Обычный `merge` по дате в этом проекте запрещён.

### Стационарность

Ценовые ряды нестационарны, а большинство ML-моделей это предполагают. Простые
разности убивают память ряда. Реализовать **дробное дифференцирование**
(fractional differentiation) с подбором минимального порядка `d`, при котором
тест Дики — Фуллера проходит, — так ряд становится стационарным, сохраняя
максимум предсказательной информации.

## 18. Разметка данных

### Тройной барьер вместо фиксированного горизонта

Разметка «вырастет ли цена через 5 дней» плоха: она игнорирует путь, которым
цена туда пришла, и не учитывает, что позицию бы закрыли по стопу.

Правильная разметка ставит три барьера от точки входа:

1. Верхний — цель по прибыли (кратно текущей волатильности)
2. Нижний — стоп-лосс (кратно волатильности)
3. Вертикальный — максимальный срок удержания

Метка = тот барьер, которого цена коснулась первым. Барьеры масштабируются
по оценке волатильности на момент входа, а не фиксированными процентами.

### Мета-разметка

Наиболее практичная схема для малого капитала и она же самая недооценённая:

- **Первичная модель** (может быть простым правилом) определяет направление.
- **Вторичная ML-модель** отвечает только на вопрос «стоит ли действовать
  по этому сигналу» — бинарная классификация с целевой переменной «сработал
  ли сигнал первичной модели».

Преимущество: вторичной модели не нужно предсказывать направление рынка —
задачу, в которой почти все проигрывают. Ей нужно лишь отфильтровать заведомо
плохие сигналы, а это задача на порядок проще и с гораздо более благоприятным
соотношением сигнал/шум. Именно эту схему реализовать первой.

### Веса наблюдений

Метки, полученные тройным барьером, перекрываются во времени: удержание с
понедельника по пятницу и со вторника по субботу используют почти одни и те же
данные. Такие наблюдения не независимы, и модель, обученная без учёта этого,
переоценивает свою уверенность.

Требование: считать конкурентность меток (сколько меток одновременно
используют каждый бар) и передавать в обучение веса наблюдений, обратные
конкурентности.

## 19. Валидация: почему стандартная кросс-валидация здесь не работает

### Запрещённые практики

Следующее в этом проекте запрещено и должно вызывать ошибку, а не
предупреждение:

- `train_test_split(..., shuffle=True)` на временных рядах
- Стандартный `KFold` / `StratifiedKFold` без очистки
- `StandardScaler.fit()` на полном датасете до разбиения
- Отбор признаков по всему датасету до разбиения
- Заполнение пропусков средним, посчитанным по всей истории

Каждый пункт — прямая утечка будущего в обучающую выборку. Все они являются
поведением библиотек по умолчанию, поэтому их нужно блокировать явно.

### Purged K-Fold с эмбарго

Стандартная реализация:

1. Разбиение по времени, без перемешивания.
2. **Очистка (purging):** из обучающей выборки удаляются наблюдения, чьи метки
   по времени перекрываются с тестовым отрезком.
3. **Эмбарго:** дополнительно удаляется буфер после тестового отрезка (обычно
   1% длины выборки) — из-за автокорреляции признаков.

Без обоих шагов оценка качества модели завышена, причём тем сильнее, чем длиннее
горизонт удержания.

### Оценка вероятности переподгонки

Реализовать комбинаторно-симметричную кросс-валидацию (CSCV) для расчёта
**вероятности переподгонки бэктеста** (PBO). Метод оценивает, насколько часто
конфигурация, лучшая на обучении, оказывается хуже медианы на проверке.

Порог приёмки: PBO выше 0,5 означает, что процедура отбора не лучше подбрасывания
монеты. Такая стратегия к боевому запуску не допускается ни при каких значениях
доходности.

## 20. Модельный слой

### Единый протокол

```python
class Model(Protocol):
    def fit(self, X, y, sample_weight) -> None: ...
    def predict_proba(self, X) -> np.ndarray: ...
    def feature_importance(self) -> dict[str, float]: ...
    def explain(self, x) -> str: ...   # объяснение на русском языке
```

Метод `explain` обязателен для всех моделей без исключения. Модель, которая не
может объяснить конкретное решение строкой, понятной заказчику, не допускается
в контур — даже в исследовательский. Это прямое следствие требования из
раздела 0.

### Лестница сложности и условия перехода

Каждая ступень открывается только после того, как предыдущая исчерпана.

| Ступень | Инструменты | Условие допуска |
|---|---|---|
| 0 | Правила без обучения | Базовая линия, всегда |
| 1 | Логистическая регрессия, Ridge, Lasso | Ступень 0 пройдена, PBO < 0,5 |
| 2 | Случайный лес, градиентный бустинг (LightGBM, XGBoost, CatBoost) | Ступень 1 даёт устойчивый OOS-результат |
| 3 | Последовательные модели (LSTM, GRU, TCN, Transformer) | ≥ 5 лет чистых признаков, ступень 2 исчерпана |
| 4 | Обучение с подкреплением (PPO, SAC) | См. предупреждение ниже |

Переход на ступень выше без выполнения условия — запрещён, независимо от того,
насколько привлекательно выглядит результат.

### Отбор признаков

Стандартная важность признаков в деревьях (MDI) смещена в пользу признаков с
высокой кардинальностью и не годится. Использовать **среднее падение точности
(MDA) на purged-разбиении** и кластеризацию коррелированных признаков перед
оценкой важности.

### Предупреждение по ступени 4

Обучение с подкреплением на финансовых рядах — область, где терпят неудачу
исследовательские группы с несравнимо большими ресурсами. Причина:
среда нестационарна, вознаграждение крайне зашумлено, а агент почти неизбежно
обучается эксплуатировать артефакты симулятора вместо реальных закономерностей.

Интерфейс закладывается. В план работ ступень 4 не ставится.

## 21. LLM в исследовательском контуре

Интеграция с Anthropic API (`research/llm.py`). Два легитимных применения и
одна фундаментальная ловушка.

### Применение 1 — генерация гипотез

LLM формулирует гипотезы, которые затем проверяются обычным пайплайном.
Обязательное условие: каждая сгенерированная гипотеза попадает в журнал
раздела 16 с пометкой источника. Генерация без записи в журнал запрещена.

### Применение 2 — текст в признак

Извлечение структурированных признаков из новостей, отчётности, сообщений
о существенных фактах. Схема: текст → LLM → числовые признаки → хранилище
признаков с обязательным `availability_lag`, равным времени публикации.

### Ловушка: ретроспективная осведомлённость модели

**Это главная опасность всей Части II, и её почти никто не учитывает.**

LLM обучена на данных до определённой даты. Если попросить её оценить
тональность новости за март 2020 года, она отвечает, **зная**, чем закончился
март 2020 года. Эта осведомлённость просачивается в признак, признак попадает
в обучающую выборку, и бэктест показывает выдающийся результат, полностью
недостижимый в реальном времени.

Утечка невидима: формально данные датированы правильно, `availability_lag`
проставлен, `merge_asof` выполнен корректно. Утечка находится не в данных,
а внутри весов модели.

### Обязательные меры

1. Любой признак, полученный от LLM, помечается флагом `llm_derived: true`.
2. Бэктест с такими признаками на периоде **до даты обучения LLM** считается
   недействительным. Система обязана отказаться выводить по нему метрики и
   вывести объяснение причины.
3. Такие признаки валидируются **только вперёд**: с момента бумажной торговли
   и далее. Это означает минимум 6–12 месяцев накопления, прежде чем по ним
   можно будет что-то утверждать.
4. Дата обучения используемой модели фиксируется в конфиге и участвует в хеше
   версии данных.

### Применение 3 — то, что действительно работает сегодня

Самое надёжное применение LLM в этом проекте — не признаки, а **аудит кода
и постановка вопросов к результатам**. Дать модели отчёт бэктеста и попросить
найти признаки утечки, подгонки или ошибок в модели издержек. Это применение
не имеет проблемы ретроспективной осведомлённости, потому что не создаёт
признаков.

## 22. Смена режима и вывод модели из эксплуатации

Модель, обученная на одном рыночном режиме, перестаёт работать при смене
режима — и это не отказ, а нормальное свойство. Систему нужно проектировать
исходя из того, что каждая модель конечна.

### Детекция

- Фильтр CUSUM для обнаружения структурных сдвигов в ряду
- Скрытые марковские модели или кластеризация для идентификации режима
  (низкая/высокая волатильность, тренд/боковик)
- Мониторинг дрейфа распределения признаков (PSI, KS-тест) между обучающей
  выборкой и текущими данными

### Критерий вывода из эксплуатации — задаётся ДО запуска

Для каждой модели в реестре обязательно указываются условия автоматического
отключения, зафиксированные до её первого боевого решения:

```yaml
модель: meta_filter_v3
условия_вывода_из_эксплуатации:
  скользящий_шарп_60д_ниже: 0.0
  просадка_модели_превышает: 0.10
  дрейф_признаков_PSI_выше: 0.25
  доля_ошибочных_фильтраций_выше: 0.60
  безусловный_срок_переобучения: 180   # дней
```

При срабатывании любого условия модель отключается автоматически, система
переходит на ступень 0 (правила без обучения) и отправляет уведомление.
Решение о возврате модели принимает человек.

Критерии, дописанные после того, как модель начала терять деньги, не имеют
силы. Смысл в том, чтобы зафиксировать их, пока результат неизвестен.

### Теневой режим

Новая модель никогда не заменяет действующую напрямую. Она сначала работает
в теневом режиме: получает те же данные, принимает решения, пишет их в журнал,
но не отправляет заявок. Минимум 3 месяца параллельной работы с прямым
сравнением. Замена — только по результатам.

## 23. MLOps и воспроизводимость

### Обязательные требования

1. **Отслеживание экспериментов.** MLflow локально. Каждый прогон логирует
   параметры, метрики, артефакты, хеш данных.
2. **Версионирование данных.** Хеш содержимого кэша входит в идентификатор
   прогона. Изменились данные — изменился прогон.
3. **Полная воспроизводимость.** Любой результат из журнала гипотез
   восстанавливается одной командой: `python -m research.reproduce <run_hash>`.
   Зафиксировать все источники случайности (`random`, `numpy`, фреймворк,
   порядок потоков).
4. **Реестр моделей.** Каждая обученная модель хранится вместе с: датами
   обучающей выборки, списком признаков и их версий, метриками валидации,
   критериями вывода из эксплуатации, хешем кода.
5. **Модель не грузится из pickle без проверки хеша.** Несовпадение — отказ
   запуска.

### Границы ресурсов

Обучение выполняется локально. GPU не требуется до ступени 3. Если задача
требует облачных вычислений — это сигнал, что выбранная сложность модели не
соответствует объёму имеющихся данных, а не повод арендовать сервер.

## 24. Условия включения ML

Фича-флаг `ml.enabled` переводится в `true` только при одновременном выполнении:

- [ ] Фазы 1–8 основной части пройдены полностью
- [ ] Бумажная торговля отработала 3 месяца без расхождений с бэктестом
- [ ] Хранилище признаков содержит ≥ 5 лет данных с проставленными задержками
- [ ] Purged K-Fold с эмбарго реализован и покрыт тестами
- [ ] Расчёт PBO реализован и покрыт тестами
- [ ] Журнал гипотез ведётся с первого дня и содержит всю историю испытаний
- [ ] Дефлированный коэффициент Шарпа выводится во всех отчётах

До выполнения всех пунктов модули `ml/` существуют, покрыты тестами на
синтетических данных, но в торговом контуре не участвуют.

## 25. Дополнительные зависимости Части II

Устанавливаются, но не импортируются в торговом контуре при `ml.enabled: false`.

```
scikit-learn          базовые модели, метрики, пайплайны
lightgbm              градиентный бустинг, ступень 2
statsmodels           тесты стационарности, структурные сдвиги
mlflow                отслеживание экспериментов
anthropic             LLM в исследовательском контуре
torch                 ступень 3, ставится позже
```

Реализации purged K-Fold, CSCV, PBO, дефлированного Шарпа, тройного барьера
и дробного дифференцирования пишутся самостоятельно — в стандартных
библиотеках их нет, а сторонние реализации часто содержат те самые утечки,
от которых должны защищать. Каждая покрывается тестом на синтетических данных
с заранее известным ответом.
